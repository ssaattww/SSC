## 指摘事項

- **[P1][blocking] 空文字列の比較 key を含む有効な既存比較結果で `GetDiffEntries()` が例外化する。** `src/SSC/ParallelPathAccessExtensions.cs:240-242` は `KeyText != null` をすべて `ParallelDiffPathSegment.Key(...)` へ渡す一方、`src/SSC/ParallelDiffPathSegments.cs:107-114` は空文字列を `ArgumentException` として拒否する。base の文字列連結経路は同じ結果を `Items[].Value` として列挙していたため、既存 API の後方互換契約（`doc/design/detail/11-DiffEntryCustomPath.md:1216-1239`）を破る。親側 probe でも base は `Items[].Value`、head は `ArgumentException` となることが実行確認済みである。public projection segment が empty key を拒否する設計自体は維持できるが、標準 path 生成用には既存 `KeyText` を損なわず扱える内部経路と回帰testが必要である。
- **[P2][blocking] 新規22個の `[Fact]` / `[Theory]` の全件に、必須の XML summary がない。** `tests/SSC.Unit.Tests/ParallelDiffPathProjectionUnitTests.cs:7` から始まる15 method、`tests/SSC.E2E.Tests/ParallelDiffPathProjectionE2ETests.cs:7` から始まる6 method、`tests/SSC.Unit.Tests/GitHubActionsTestArtifactContractUnitTests.cs:5` の1 methodはいずれも属性直前に `/// <summary>` がない。`source-documentation-policy` の test documentation blocking rule に反する。各 test classにも contractを示す class-level summaryがなく、共用される nested fixture/test doubleの文書化も不足している。
- **[P2][blocking] 新規 internal API surface の XML documentation が不足している。** `src/SSC/Internal/ParallelDiffPathFormatter.cs:6-16` の internal classと2 method、`src/SSC/ParallelDiffPathSegments.cs:49-56` の internal factory、`src/SSC/ParallelDiffPathProjection.cs:26-34`、`:52-65`、`:182-192` の internal constructorに XML summaryがない。新規公開型・公開memberの大半には XML documentation があるが、`source-documentation-policy` は internal APIも必須としているため review gateを閉じられない。なお既存 `src/SSC/ParallelPathAccessExtensions.cs:5-48` の classと従来4 public methodにも同じ既存不足が残る。
- **[P2][non-blocking/held] package READMEと既存公開API設計の利用導線が新機能へ接続されていない。** NuGet packageに同梱される `README.md:153-210` は `GetDiffEntries()` までしか説明せず、`GetDiffEntryPathProjections()`、projector実装例、projected pathはnode lookup住所ではないこと、重複を許すこと、全segment省略時・projector例外の契約を記載していない。`doc/design/detail/02-PublicApi.md:97-113` の公開API一覧と `doc/design/README.md:7-18` の索引にも新API／`11-DiffEntryCustomPath.md` が追加されていない。設計書を直接知る利用者は目的を達成できるため held とするが、公開機能としての発見性と契約理解に残余リスクがある。
- **[P2][non-blocking/held] 新設計書の標準path解決契約が container presence の既存契約と矛盾する。** `doc/design/detail/11-DiffEntryCustomPath.md:80-88` と `:758-763` は標準pathを一律に `GetNodeByPath()` で解決できるように記載するが、同文書 `:920-932` と既存の authoritative contract `doc/design/detail/02-PublicApi.md:446-468` は `ContainerPresence` では `Node == null` で解決を保証しない。`Kind == Node` に限定しない説明は利用者を誤誘導するため、既存契約に合わせた限定が必要である。
- **[P2][non-blocking/held] `ProjectedParentPath == null` の意味が公開契約に不足している。** `src/SSC/ParallelDiffPathProjection.cs:204-207` は「標準 parent path と同じ segment 範囲」とだけ記載する一方、`src/SSC/ParallelPathAccessExtensions.cs:326-345` はroot直下に加え、parent範囲の全segmentが `Omit()` された場合も `null` を返す。`doc/design/detail/11-DiffEntryCustomPath.md:780-817` も後者を定義していない。`Entry.ParentPath` を併用すれば回避できるため held とするが、null意味を XML/designの双方で明示する必要がある。
- source layoutについては、dotted responsibility file、誤ったfolder placement、partial type layout、設計書と実ファイルpathの不一致は確認されなかった。escape（`]`、`\\`、先頭`#`）、key/ordinal区別、null/missing/container presence、重複 `ProjectedPath`、例外伝播、CI artifact uploadの実装と新規testには、上記以外の blocking findingは確認されなかった。user-confirmation-required findingはない。
